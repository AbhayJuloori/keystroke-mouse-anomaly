A password proves you know a secret. How you type it and how you move the mouse says whether you are the person who usually knows it. 01 · Keystroke

Four detectors, one fixed protocol

The CMU Keystroke Dynamics benchmark has 51 people typing .tie5Roanl 400 times across 8 sessions, 20,400 samples with 31 timing features each. Following Killourhy and Maxion, each user's model trains on sessions 1 to 4, is tested on that user's sessions 5 to 8, and faces 250 impostor attempts from the other 50 users. The score is equal error rate: the point where false accepts equal false rejects.

02 · Mouse

Movement has a signature too

Balabit sessions are raw pointer events. Each session is cut into actions at clicks and at pauses over 10 seconds, then every action becomes speed, acceleration, jerk, angular velocity, curvature, straightness, direction and click hold time. A per-user classifier learns that user's actions against everyone else's training actions. Move inside the pad to see the same features computed live.

03 · Risk score

One number, three reasons

The session risk score (0 to 100) combines the mouse anomaly score, eight per-user deviations (speed, curvature, straightness, click hold, acceleration, angular velocity, action duration) and three device flags: emulator, rooted device, VPN. The device flags are synthetic, generated from a seeded config at higher rates for impostor sessions, because no public dataset pairs mouse sessions with device signals. SHAP values on the final model become the top three reasons.

04 · Time split

Later attempts never train the model

Random splits leak the future: a model that has seen tomorrow's typing looks better than it will be. Both datasets are split by time for every user, and the pipeline checks the split in code.

      05 · Drift

      Watching each user's scores

      /drift/{user_id} compares a rolling window of the scores a user has been served against scores the model never trained on, using population stability index (PSI). The replay below sends each user's genuine traffic through the API, then impostor traffic, and reads the drift endpoint at every checkpoint.

      Checkpoint after genuine trafficCheckpoint after impostor trafficPSI 0.2 alert line
      Drift replay at PSI 0.2
      ChannelUsersFalse drift, genuineCaught, all-impostor window

      Minimum windows come from sampling noise: with 10 bins, PSI under no change is about 9 × (1/n + 1/m), and the window must keep that under half the alert line. That gives 164 scores for keystroke.

      Why keystroke drift fires on real users

      Median genuine score relative to the reference, by CMU session. People type the password differently as they practice it. On genuine traffic, a drift flag here means re-enroll the user, not an attack. The project reports this instead of raising the alert line after seeing it.

      06 · Serving and tracking

      From notebook numbers to an API

      One command (make all) trains every model, logs every run to MLflow, writes the artifacts, replays traffic through the API, and regenerates the README and figures from results.json. The pipeline then reads MLflow back and fails if any fixed-threshold false accept or false reject metric is missing.

      FastAPI endpoints
      • POST
        /score/keystroke31 timing features for a claimed user. Returns score, threshold, decision. p50 ms, p95 ms.
      • POST
        /score/sessionRaw mouse events and optional device flags. Returns risk 0 to 100, decision and three reasons. p95 ms for 250 events.
      • GET
        /drift/{user_id}PSI of the user's recent scores against their reference, with a verdict once the window is large enough.
      • GET
        /healthArtifact status.

      Limits. 51 typists and 10 mouse users are far too few for fairness claims or real identity decisions. The password is fixed text. Device signals are simulated. There is no live traffic. This is a careful benchmark study with a serving path, not a production system.
